# Устройство записи

Технические заметки для участников проекта. Начните с [README](../README.md),
если вам нужна установка или управление приложением. Примеры VA-конвейера
относятся к `vah264enc`; программный `x264enc` использует другой путь преобразования.

## Конвейеры

Захват:

```
<source>
  ! vapostproc ! video/x-raw(memory:VAMemory),format=NV12
  ! videorate ! video/x-raw(memory:VAMemory),format=NV12,framerate=60/1
  ! vah264enc rate-control=vbr bitrate=15000 key-int-max=60
  ! h264parse config-interval=-1
  ! video/x-h264,stream-format=byte-stream,alignment=au,profile=high
  ! appsink name=sink
```

**Порядок `vapostproc` перед `videorate` принципиален.** Портал отдаёт кадры
как `video/x-raw(memory:DMABuf)`, а фильтр вида `video/x-raw,framerate=60/1`
без признака памяти матчится только с системной — фичи caps должны совпадать
точно. Фильтр частоты сразу после `pipewiresrc` ронял захват с экрана в
`not-negotiated`, хотя на `videotestsrc` всё работало. `vapostproc` принимает
и DMABuf, и системную память, поэтому импорт идёт первым, а частота
приводится уже в VA-памяти. Побочно это дешевле: преобразуются только
реально пришедшие кадры, дубликаты добавляются после.

Сохранение (ремьюкс, без перекодирования):

```
appsrc ! h264parse ! mp4mux faststart=true ! filesink
```

Видео и звук заливаются в свои `appsrc` из двух потоков: mp4mux выравнивает
дорожки по времени, и последовательная заливка клипа крупнее очереди appsrc
(200 КБ) вставала намертво. Пока потоки работают, главный слушает шину:
если мультиплексор падает посреди записи, appsrc перестаёт разбирать очередь,
и `push_buffer` с `block=true` уснул бы навсегда. По ошибке на шине конвейер
переводится в NULL — это будит заблокированные потоки, а недописанный файл
удаляется (`tests/mux_error_no_hang.rs`).


### Почему звук живёт в том же конвейере, что и видео

Только так у веток общие часы и сравнимые метки времени, по которым потом
режется клип. Метки берутся как **running time**, а не сырой PTS: базовый
класс GstVideoEncoder сдвигает выход `vah264enc` на 1000 часов вперёд
(`min-pts`), чтобы DTS не уходил в минус при переупорядочении кадров.
Звуковые кодировщики так не делают. На сырых PTS ветки оказываются в разных
системах отсчёта, и в окно клипа попадает ровно один звуковой кадр — тест
`capture_with_audio_produces_two_tracks` это проверяет.

В микшер всегда подмешивается `audiotestsrc wave=silence`: монитор вывода
молчит, пока в системе ничего не играет, и без гарантированно живого входа
у клипа могло не оказаться звуковой дорожки вовсе.

### Звуковые дорожки

Режим звука выводится из трёх полей конфига — `system`, `mic` и
`separate_tracks` (`AudioConfig::mode`), поэтому конфиги прошлых версий
означают то же, что и раньше: оба источника — одна смешанная дорожка.

| Режим                | Дорожек в mp4 | Что в них                        |
|----------------------|---------------|----------------------------------|
| без звука            | 0             | —                                |
| только системный     | 1             | монитор вывода                   |
| только микрофон      | 1             | микрофон                         |
| смешанный            | 1             | монитор + микрофон через микшер  |
| раздельные дорожки   | 2             | 1 — монитор, 2 — микрофон        |

У каждой дорожки своя ветка: `audiomixer` (только источник и тишина) →
кодировщик → свой `appsink` → свой `AudioRingBuffer`. В раздельном режиме
системный звук и микрофон не встречаются ни в одном элементе. Все ветки
живут в одном конвейере с видео и метятся running time, поэтому срез идёт по
общей шкале: `snapshot_range` каждой дорожки берёт окно видеоклипа.

```
bin.( name=src_mic pulsesrc ) ! audioconvert ! audioresample ! caps
  ! volume ! level name=level_mic ! amix_mic.
audiotestsrc wave=silence ! … ! amix_mic.
audiomixer name=amix_mic ! … ! avenc_aac ! aacparse ! appsink name=asink_mic
```

Источник обёрнут в именованный bin: ошибку любого его элемента можно отнести
к источнику по предкам (`AudioSource::owning`). Отказ при запуске
(`set_state` вернул ошибку, на шине — ошибка из `src_*`) — поток захвата
пересобирает конвейер без этого источника и показывает «недоступен». Отказ
посреди записи — ошибка не останавливает конвейер: basesrc после неё шлёт
EOS, микшер дорожки отпускает этот вход и продолжает на тишине, так что
число дорожек в клипе не меняется. Повторная попытка — по «Применить».
Тип bin в описании указан явно (`bin.(`): голая скобка сразу после ссылки
`amix_sys.` разбирается как bin типа `amix_sys`.

`level` после громкости присылает пик раз в 0,5 с; поток захвата пишет его в
`SourceMeter`, откуда GUI показывает «сигнал / тишина / нет данных /
недоступен». Цена — одно сообщение шины в полсекунды на источник.

При сохранении у каждой дорожки свой `appsrc` и свой поток заливки — та же
схема, что спасает от взаимной блокировки с mp4mux, просто для N дорожек
(`tests/audio_tracks.rs`, 120 с с двумя дорожками). Перед срезом сохранение
до 0,4 с ждёт, пока звук догонит последний видеокадр: звуковая ветка
отстаёт на задержку источника, микшера и кодировщика, и без ожидания конец
клипа оставался без последней доли секунды звука.

Клип пишется под именем `*.mp4.part` и переименовывается только после EOS
мультиплексора: падение посреди записи не оставляет в библиотеке файл без
moov, а огрызки прошлого запуска убираются при старте.


## Выбор кодировщика видео

`src/encoders.rs`. В настройке — `encoder: "auto"` или имя элемента и
`video_codec: "h264" | "h265"` (`"av1"` — только из командной строки, как
эксперимент). Старые значения `"Vah264enc"`, `"Vah264lpenc"`, `"X264enc"`
читаются как ручной выбор того же элемента.

Кандидат — элемент плюс всё, что нужно для его включения: цепочка до него
(`vapostproc` → VA-память для VA-API и Quick Sync на Linux, `videoconvert` →
системная память для остальных), свойства (битрейт, интервал ключевых
кадров в кадрах, B-кадры выключены: буфер хранит только PTS, и сохранение
ставит DTS = PTS) и caps после парсера. Профиль `high` требуется только у
VA-API и x264: openh264enc его не умеет и падал в not-negotiated.

Проверка кандидата, по порядку:

1. Нет фабрики и нет плагина — «плагин не установлен».
2. Нет фабрики, но плагин есть — «устройство или драйвер не подошли»: VA и
   nvcodec регистрируют элементы только под найденное железо. Имена VA
   зависят от устройства (`varenderD129h264enc`), поэтому VA-кандидаты
   берутся из реестра.
3. Пробное кодирование 5 кадров 320×240 через ту же цепочку, парсер и caps,
   что и захват, с таймаутом 5 с. Ошибка разбора свойства или устройства —
   «не открылся», not-negotiated — «несовместимый формат».

Поток захвата проверяет только кодек текущих настроек (на этой машине,
debug-сборка: первый VA-кодировщик ~1 с — это загрузка драйвера, остальные
десятки миллисекунд); прочие кодеки окна проверяет фоновый поток, который
поток захвата дожидается при остановке — выход посреди пробного
кодирования ронял процесс внутри драйвера VA.

Критерии автовыбора: кодек совпадает; проверка пройдена; аппаратный раньше
программного; среди аппаратных — VA-API (кадр с портала не покидает
видеопамять), затем драйверы производителей с управлением битрейтом (NVENC,
Quick Sync, AMF), затем Media Foundation и Direct3D 12, low-power VA —
последним (только постоянный квантователь). О скорости кодировщиков ничего
не утверждается. Ручной выбор ставится первым, остальные — запасными.

Если кодировщик, прошедший проверку, падает в настоящем конвейере — ошибка
пришла от `venc` или `vup` (цепочка перед ним) либо конвейер не собрался из
‑за его свойств, — он попадает в список отвергнутых до следующей пересборки
по команде пользователя, и конвейер собирается со следующим. Причина видна
в окне. not-negotiated от источника (скажем, нулевая ширина кадра) — не
повод перебирать кодировщики. Сама настройка при откате не меняется.

Кодек кадров в буфере хранится в `Recorder` вместе с активным
кодировщиком; сохранение берёт парсер и caps от него (`write_clip_as`).
HEVC пишется в mp4 как `hvc1` (h265parse выбирает сам). У AV1 нет
config-interval: заголовок последовательности обязан идти в каждом
ключевом TU от кодировщика — svtav1enc и av1enc так и делают (проверено),
про аппаратные AV1-кодировщики это не проверено, поэтому AV1 в окне нет.

Диагностика: `replay-rs --list-encoders` печатает таблицу проверки и
причину автовыбора; та же таблица — в окне, «Диагностика кодировщиков».

## Просмотр и обрезка

`src/media.rs` — разбор mp4 через qtdemux без декодирования: потоки,
длительность, время ключевого кадра не позже заданного (точный переход
qtdemux начинает с ключевого кадра; проба взводится только после
FLUSH_STOP перехода, иначе отвечал буфер, ушедший до него). Перед каждым
fakesink стоит `queue`: у qtdemux один поток, и приёмник без очереди
останавливал его на preroll — PAUSED не наступал. Пустой, битый,
недописанный (без moov) или исчезнувший файл — ошибка за секунды, а не
зависание (`tests/trim_player.rs`).

`src/player.rs` — playbin с `videoconvertscale ! RGBA ≤1280×720, PAR 1/1 !
appsink max-buffers=1 drop=true sync=true`. Масштаб считает GStreamer с
сохранением пропорций (1920×1080 → 1280×720, 2560×1080 → 1280×540,
вертикальное 720×1280 → 405×720). Appsink хранит последний `Sample`, пиксели
копируются один раз — при показе, в текстуру egui; кадры, которые окно не
успело показать, не копируются вовсе. Плеер открывается в фоновом потоке
(ждёт первый кадр: до этого playbin не знает числа дорожек) и живёт, пока
открыт просмотр: `Drop` переводит его в NULL, освобождая декодер. С
конвейером захвата он ничего не делит. Звук плеера идёт на устройство
вывода по умолчанию — и, значит, попадает в системную дорожку фоновой
записи, как и любой другой звук системы.

Переключение дорожки — `current-audio` playbin; выбор применяется, когда
пошли данные, поэтому окно показывает выбор пользователя, а не свойство.

`src/trim.rs` — обрезка в новый файл `replay_<имя>_cut_<начало>-<конец>.mp4`
рядом с оригиналом (оригинал не меняется; префикс `replay_` — чтобы
недописанный `.part` убрала уборка при старте). Оба режима: qtdemux → проба
на каждом его выходе (диапазон) → ветка → mp4mux, дорожки в исходном
порядке. Поток, который не на чем пересобрать, — отказ, а не молчаливая
потеря дорожки; после записи число потоков результата сверяется с
исходником.

* Быстрый: без перекодирования, видео с ключевого кадра K ≤ начала, звук —
  с первого кадра не раньше K; `pad.set_offset(-K)` — результат с нуля.
  Окно заранее показывает фактическое начало. Обрезка 15 с из 5‑минутного
  клипа — ~70 мс.
* Точный: видео декодируется с K, кадры до начала выбрасываются после
  декодера, кодирование — тем же кодировщиком, что пишет захват (или
  автовыбором под кодек исходника); звук перекодируется тем же кодеком.
  Точность начала — кадр; звук начинается с первого кадра не раньше начала
  (до ~21 мс тишины), шкала общая, синхронность сохраняется.

Экспорт идёт в своём потоке, с прогрессом и отменой; закрытие просмотра
отменяет его. Результат пишется в `.part` и переименовывается после
проверки.

## Оверлей

`src/overlay/`. Отдельный поток читает `Recorder` и `CaptureService` (второго
конвейера нет) и зовёт `Recorder::save` в своём потоке. Выключенный оверлей
спит на канале до «Применить» и не держит соединения с композитором; если
оверлей не удалось показать, запись это не затрагивает.

Отрисовка программная: egui строит треугольники и атлас шрифтов,
`raster.rs` закрашивает их в буфер ARGB с premultiplied alpha
(барицентрика, ближайший сосед, «source over»). Карточка 300×128 (одна
строка — 300×38) перерисовывается не чаще двух раз в секунду и только когда
изменилось её содержимое. Так рядом с игрой не появляется второй
GL-контекст, а картинка проверяется в тесте без дисплея
(`REPLAY_OVERLAY_DUMP=<папка> cargo test overlay` сохраняет JPEG).

* **Linux / Wayland** — `zwlr_layer_shell_v1`, слой `overlay`, без
  клавиатурного фокуса (`KeyboardInteractivity::None`); в режиме «клики
  насквозь» — пустая область ввода. Буфер — `wl_shm`. Крейт
  smithay-client-toolkit 0.19 уже был в дереве зависимостей (через winit),
  новых крейтов нет. Проверено на KDE Plasma 6: слой создаётся, композитор
  подтверждает размер, кадры прикрепляются (`WAYLAND_DEBUG=client`).
  Без layer-shell (GNOME, gamescope) — обычное окно `xdg_toplevel`, о чём
  пишет окно настроек.
* **Windows** — popup-окно `WS_EX_LAYERED | TOPMOST | TOOLWINDOW |
  NOACTIVATE` (+ `TRANSPARENT` для «кликов насквозь»), кадр через
  `UpdateLayeredWindow`. Никаких хуков и внедрения в процесс игры.
  Собирается (`cargo check --target x86_64-pc-windows-gnu`), на
  оборудовании не проверялось; DPI-масштаб не учитывается.

Гарантий показа поверх полноэкранной игры нет ни на одной платформе:

| Где                                   | Поверх полноэкранной игры           |
|---------------------------------------|-------------------------------------|
| KDE Plasma (KWin), wlroots            | да; KWin при этом выключает игре прямой вывод (direct scanout) и композитит кадр |
| GNOME (Mutter)                        | нет layer-shell — обычное окно      |
| gamescope (Steam Deck, игровой режим) | нет layer-shell — обычное окно      |
| Windows, окно без рамки / flip-модель | да                                  |
| Windows, эксклюзивный полноэкранный   | нет                                 |

Из-за цены для direct scanout есть режим «только после сохранения»: оверлей
появляется на 4 с после сохранения и уничтожает поверхность.

Запасные пути: системное уведомление после сохранения (настройка; на Linux
`notify-send`, на Windows — всплывающая подсказка значка в трее) и подсказка
значка в трее: буфер, кодировщик, микрофон, последнее сохранение.

## Измерения

Intel i5-1135G7 (TigerLake, VA-API), Arch, GStreamer 1.28.8, release-сборка,
`--mode test --headless`, 1280×720@60, 8 Мбит/с, 15 с записи, по два прогона.
Процессорное время всего процесса (user+sys); в тестовом режиме основную
его часть даёт генерация кадров `videotestsrc`, поэтому важна разница, а не
абсолют.

| Что сравниваем                                   | CPU за 15 с         | Пиковый RSS |
|--------------------------------------------------|---------------------|-------------|
| До изменений (`d20928e`), системный звук         | 9,10 / 9,30 с       | ~217 МБ     |
| После, системный звук (индикатор `level`)        | 9,15 / 9,15 с       | ~217 МБ     |
| После, без звука, оверлей выключен               | 8,51 / 8,37 с       | ~207 МБ     |
| После, без звука, оверлей «всегда»               | 8,60 / 8,80 с       | ~208 МБ     |

Обнаружение кодировщика H.264 при запуске — ~180 мс (первый VA-кодировщик
загружает драйвер), остальные кодеки проверяются в фоне. Быстрая обрезка
15 с из 5-минутного клипа — ~70 мс.
